# PROJECT_PLAN.md

`14_4팀_신호정.ipynb`의 작업 계획 문서입니다. 노트북의 각 섹션 `계획 확인`(X-a) 셀은 이 문서와 지금까지의 수행 내역을 근거로 작성합니다.

## A-b. 프로젝트 수행 계획

1. 한국어 친화적이며 on-device에 탑재 가능한 LLM 모델을 탐색, 선정합니다.
    - Hugging Face에서 선호도에 따른 후보를 추려 정리합니다.
    - 웹 검색 및 AI 서포트를 통해 최적의 모델을 선발합니다.
    - 선정 기준: 한국어 성능 / 속도·메모리(1.5~3B Q4 영역) / 라이선스 / GGUF 변환·양자화 가용성
2. on-device 탑재용 임베딩 모델을 별도로 탐색, 선정합니다.
    - 선정 기준: 한국어 Retrieval 성능(MTEB-ko 등) / ONNX 변환 용이성 / 토크나이저 C# 포팅 가능성(`Microsoft.ML.Tokenizers` 우선) / 경량 차원·모델 크기·Prefill 비용 / prefix 규칙(`query:`/`passage:`)
3. on-device LLM 탑재 기술을 탐색·평가하여 채택합니다. (LLMUnity vs GGUF 직접 통합, Android 배포 제약 확인)
4. 선정 기술로 Unity 상에 LLM을 이식하여 최소 구동을 조기 검증합니다. (Editor 1차 → Galaxy S25 2차)
5. `2024년_원천징수의무자를_위한_연말정산신고안내.pdf` 문서를 확인합니다. (PDF 로더, 분량·내용·표 비중/구조)
6. 표 인식형 추출 + 하이브리드 Chunking을 수행합니다. (표는 격자 보존→마크다운/HTML, header-aware 분할, 본문 의미 단위 분할)
7. 임베딩 모델을 ONNX로 변환하고 수치 패리티를 검증합니다. (PyTorch 대비 코사인 ≥ 0.999, Pooling·L2·prefix 고정)
8. ONNX 모델로 청크를 임베딩하여 배포용 인덱스 파일을 생성합니다. (기기와 동일 아티팩트로 벡터 공간 불일치 방지, 동일 양자화 적용)
9. 프로토타입 검색기를 구성합니다. (인덱스 파일 brute-force 코사인 검색 기준, VectorDB는 오케스트레이션 보조)
10. 프로토타입 런타임을 준비합니다. (LLM 런타임 구동, 호환 토크나이저, 생성 파라미터 튜닝)
11. 맥락 기반 답변을 생성하는 RAG 시스템을 플로우차트로 설계합니다. (검색 점수 임계값 라우터 노드 선반영)
12. 설계 검토 후 LangGraph로 RAG 시스템을 구현합니다.
13. RAG 성능을 검색 측/생성 측으로 분리 검증합니다. **(과제 목표 지점)**
    - 골든 Q&A 셋(정답+근거 청크 라벨) / 검색 측 Context Recall·Precision / 생성 측 Faithfulness ≥ 0.8·Answer Relevancy / 표본 50개 이상 또는 신뢰구간 병기
14. ipynb 구현을 Unity 엔진으로 포팅합니다. (동일 GGUF, ONNX 이식, C# 코사인 검색, `Microsoft.ML.Tokenizers`, C# RAG 상태기계, prefix·토큰 ID 패리티)
15. Unity 포팅 기능들의 작동을 검증합니다. (질의 경로 임베딩 패리티 샘플 검증)
16. 어플리케이션 서비스 로직과 UI를 개발합니다. (토큰 스트리밍으로 TTFT 체감 개선)
17. 어플리케이션 구동을 검증합니다. (Editor 1차 → Galaxy S25 2차, 최초 실행 시 `persistentDataPath` 복사 흐름)
18. 처리속도·답변품질을 정량 측정 후 개선합니다. **(1차 목표 지점)**
    - 속도: decode 256토큰 기준 wall-clock ≤ 15초, prefill·decode·TTFT 분리 측정 / 품질: 13항 게이트 Editor 재측정 / 개선: 더 작은 모델·로직 최적화·top-k 축소·컨텍스트 압축
19. 로컬 LLM + 한정 인덱스의 답변 한계 측정법을 탐색합니다. (범위 밖 질의 탐지 = 최상위 코사인 점수 분포 분석)
20. LLM API 기반 Fallback을 설계합니다. (1차 라우팅 = 검색 점수 임계값, logprob 확신도는 보조 신호)
21. 설계 검토 후 RAG 시스템을 확장 구현합니다. (LangGraph 라우터 노드 → C# 상태기계)
22. Fallback 작동·품질을 검증합니다. (범위 내/밖 질의 셋으로 라우팅 정확도·답변 품질 확인)
23. Unity 어플리케이션에 다시 이식하여 APK 빌드 후 작동을 확인합니다. **(2차 목표 지점)**

## 작업 진행 규칙

- **단일 패스 우선**: 개발 프로세스 전반의 경험이 목표이므로 투기적 반복 실험·튜닝은 하지 않는다. 측정은 1회 수행하고, 작동 실패 등 부득이한 경우에만 되돌려 재작업한다.
- 작업은 **B ~ X 까지 섹션 별로** 나눠 진행합니다.
- **B ~ W** 섹션은 각 `계획 확인`(X-a) 셀에서 A-b 수행 계획과 지금까지의 수행 내역을 고려한 수행 계획을 요약 설명합니다.
- 섹션/하위 구성 법칙을 준수합니다: `## 섹션`은 알파벳 순(B, C, …), 하위는 `### X-a`, `### X-b` … 순. 각 섹션의 첫 하위는 `계획 확인`(X-a)으로 시작합니다. (X 섹션은 결론이므로 `계획 확인` 없이 `정량 결과 요약`으로 시작)
- 코드셀 주석은 한글로 작성하고 구분선 없이 심플하게 구성합니다.
- 코드셀 출력에는 이모지를 넣지 않고 구분선을 넣지 않습니다.

## 단일 패스에서 놓치기 쉬운 1회 보강 항목

반복 실험이 아니라 **각 1회**로 끝나며, 후반 재작업(작동 실패)을 예방하는 저비용 항목만 둔다.

- (A-d) 핵심 패키지 버전 고정 — ONNX 패리티가 라이브러리 버전에 민감하므로 1회 기록.

- (L) 프롬프트 템플릿 설계 — 컨텍스트 주입 포맷·시스템 프롬프트·인용 규칙. Faithfulness의 핵심 변수이므로 처음에 한 번 제대로 정의(반복 튜닝 아님).
- (R) 리소스 1회 측정 — 속도(prefill/decode/TTFT)와 함께 peak RAM·로드시간·APK 용량도 같이 기록(개선 루프 없이 측정만).
