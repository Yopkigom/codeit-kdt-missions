# 영화 리뷰 감성 분석 웹 서비스

과제 식별: [스프린트 미션 18](https://www.codeit.kr/topics/studyGroupStep6985c0d690c7e12606331077/lessons/14114)  
작성: 2026.07.30 신호정  

Streamlit(프론트엔드), FastAPI(백엔드), ONNX 모델 서빙을 하나의 서비스로 통합한  
3-tier 웹 애플리케이션입니다.

접속 URL : https://movie-review-sentiment-mi18.streamlit.app/

## A. 서비스 개요

### A-a. 목적

영화 정보를 관리하고, 사용자가 남긴 리뷰의 감성을 자동 분석해 **영화 평점으로 환산**하는 서비스입니다.
스프린트의 마지막 미션으로, 앞선 미션에서 따로 다뤘던 세 영역을 하나로 합치는 데 목적이 있습니다.

- 미션 17: Streamlit 단일 앱 + ONNX 추론
- **미션 18: 백엔드 분리, DB, REST API가 더해진 3-tier 구성**

핵심 제약은 **모든 데이터를 백엔드가 소유한다**는 것입니다. Streamlit 쪽에는 로컬 파일이나
세션 영속화 같은 별도 저장 기능을 두지 않았습니다.

### A-b. 기능

가이드가 구분한 필수 / `심화` 경계를 그대로 따랐습니다.

| 구분 | 프론트엔드 (Streamlit) | 백엔드 (FastAPI) |
|---|---|---|
| **필수** | 영화 목록(제목, 포스터, 평균 평점), 영화 추가 폼 | 영화 등록, 전체/단건 조회, 삭제 |
| **`심화`** | 리뷰 등록, 감성 분석 결과 표시, 최근 10개 리뷰 | 리뷰 CRUD, 평점 조회(감성 점수 평균), 감성 분석 |

### A-c. 기술 스택

| 계층 | 사용 기술 | 선택 이유 |
|---|---|---|
| 프론트엔드 | Streamlit 1.55 | 가이드 지정. 화면만 담당하고 상태를 갖지 않습니다 |
| 백엔드 | FastAPI 0.115 + SQLAlchemy 2.0 | OpenAPI 문서 자동 생성이 제출 항목과 직결됩니다 |
| DB | SQLite | 단일 인스턴스 데모 규모에 충분하고 별도 서버가 필요 없습니다 |
| 모델 서빙 | onnxruntime 1.28 + tokenizers 0.23 | `transformers` 없이 추론. 메모리 예산에 직접 영향 |
| 컨테이너 | python:3.12-slim | Cloud Run 배포 대상 |

### A-d. 감성 스칼라와 평점 환산

감성 라벨을 **부정 -1, 중립 0, 긍정 +1** 스칼라로 두고, 영화 평점은 소속 리뷰 스칼라의
산술평균(-1 ~ +1)으로 정의했습니다. 화면에는 `(x + 1) / 2 * 5`로 **0~5 별점으로 환산해서만**
표시하며, DB와 API 응답은 원값을 유지합니다.

**리뷰가 없으면 평점은 `null`입니다.** 0으로 바꾸지 않았습니다. 0은 이미 '중립'이라는 의미를
갖고 있어서 리뷰 없음과 중립 평가가 구분되지 않기 때문입니다. 화면에는 `평점 없음`으로 적습니다.

## C. 데이터베이스 구조도 (ERD)

```mermaid
erDiagram
    MOVIE ||--o{ REVIEW : "리뷰를 가진다"

    MOVIE {
        integer id PK "자동 채번"
        integer tmdb_id "TMDB 원본 ID, unique, nullable"
        text title "제목"
        date release_date "개봉일"
        text director "credits에서 추출"
        text genre "장르"
        text poster_url "URL만 저장"
        real external_rating "TMDB vote_average 0~10"
        boolean is_seed "시드 데이터 여부, 배포본 삭제 보호"
    }

    REVIEW {
        integer id PK "자동 채번"
        integer movie_id FK "ON DELETE CASCADE"
        text author "작성자"
        text title "제목"
        text content "내용"
        datetime created_at "정렬 기준"
        text sentiment_label "부정, 중립, 긍정"
        integer sentiment_score "-1, 0, +1"
        real confidence "max softmax, 표기용"
        text model_version "평균 오염 방지"
    }
```

### C-a. 평점 필드를 둘로 나눈 이유

`external_rating`(TMDB 수집값, 0~10)과 `sentiment_rating`(리뷰 감성 평균, -1~+1)은
**출처도 범위도 다른 별개의 값**입니다. 한 컬럼에 담으면 한쪽이 다른 쪽을 덮어씁니다.
화면에서도 이름을 붙여 나란히 보여줍니다.

`sentiment_rating`은 **컬럼이 아니라 파생값**입니다. 캐시 컬럼으로 두면 리뷰 등록, 리뷰 삭제,
영화 삭제 세 경로에서 갱신해야 하고, 한 곳만 빠뜨려도 화면의 평점이 틀어집니다.
현재 규모(리뷰 72건)에서는 `LEFT JOIN` + `AVG` 한 0번으로 충분하며, 실측 조회 지연은 3.8ms입니다.

### C-b. 삭제와 무결성

영화 삭제 시 리뷰는 FK의 `ON DELETE CASCADE`로 **DB가 함께 지웁니다.** 애플리케이션 코드로
리뷰를 먼저 지우고 영화를 지우면 중간 실패 시 고아 데이터가 남습니다.

주의할 점은 **SQLite가 외래 키 제약을 기본으로 끄고 있다**는 것입니다. 연결마다
`PRAGMA foreign_keys=ON`을 실행하지 않으면 CASCADE가 무시되고 테스트에서도
통과해 버립니다(인지하기 힘듬). 연결 이벤트에 PRAGMA를 걸고, 연쇄 삭제를 테스트로 고정했습니다.

### C-c. 중복 방지

- `tmdb_id`에 UNIQUE. 단 nullable입니다. 화면에서 수동 등록한 영화에는 TMDB ID가 없기 때문입니다.
- `(title, release_date)` 복합 UNIQUE. 같은 제목의 리메이크는 개봉일이 달라 통과합니다.

### D-b. 상태 코드와 예외 처리

| 코드 | 상황 |
|---|---|

## E. 모델 서빙

### E-a. 미션 13 자산 재사용과 경량화

가이드는 "적절한 모델 리서치"와 "**모델 경량화 방식에 대한 고민**"을 요구합니다.
미션 13에서 이미 한국어 감성 분석 모델을 학습하고 ONNX로 변환해 두었으므로,
**재학습 없이 그 자산을 그대로 재사용**했습니다.

미션 13에서 비교한 6개 조합의 결과가 이번 선택의 근거입니다.

| 조합 | ONNX 크기 | test F1 | test Acc | p50 |
|---|---|---|---|---|
| **KcELECTRA-small Full FT (선정)** | **63.3MB** | **0.856** | **0.885** | 29ms |
| KcELECTRA-small LoRA | 63.3MB | 0.843 | 0.874 | 32ms |
| KcELECTRA-small Freeze | 63.3MB | 0.624 | 0.713 | 28ms |
| KoMiniLM Full FT | 88.8MB | 0.869 | 0.897 | 28ms |
| KoMiniLM LoRA | 88.8MB | 0.847 | 0.877 | 34ms |
| KoMiniLM Freeze | 88.8MB | 0.745 | 0.802 | 30ms |

정확도만 보면 KoMiniLM Full FT가 가장 높지만 **크기가 40% 큽니다.** 경량화 관점에서
크기 기준을 먼저 통과시키고 그 안에서 정확도를 골랐습니다.

경량화를 위해 서빙 단계에서 추가로 택한 선택은 두 가지입니다.

1. **`transformers`를 설치하지 않습니다.** 미션 13이 남긴 `tokenizer.json`은 Rust 구현체인
   `tokenizers` 패키지만으로 로드됩니다. `transformers`를 넣으면 의존성이 크게 늘고
   경우에 따라 torch까지 끌려옵니다. 실측 피크 메모리 168MiB는 이 선택의 결과입니다.
2. **세션은 `lifespan`에서 1회만 생성합니다.** 요청마다 `InferenceSession`을 만들면
   모델 파일을 매번 다시 읽습니다.

### E-b. 모델 사양과 라벨 매핑

| 항목 | 값 |
|---|---|
| 구조 | ELECTRA 계열, hidden 256, 12 layers, vocab 54,343 |
| 파일 | `.onnx` 63MB + `.onnx.data` 63MB (external data, **짝이 맞아야 로드됩니다**) |
| 입력 | `input_ids`, `attention_mask`, `token_type_ids`, 각 `[1, 256]` **int32** |
| 출력 | `logits [1, 3]`, **raw logit** (softmax 미적용) |

`config.json`의 `id2label`은 `LABEL_0~2`뿐이라 의미를 담고 있지 않습니다.
**인덱스를 추측해 쓰면 평점의 부호가 통째로 뒤집힙니다.** 아래 두 근거로 확정했습니다.

1. 미션 13 학습 코드의 `LABEL_MAP = {'-1': 0, '0': 1, '1': 2}`
2. 골든 케이스 9건 추론 실측 (8건 일치, 불일치 1건은 중립)

| 인덱스 | 감성 | 스칼라 | 화면 표기 |
|---|---|---|---|
| 0 | 부정 | -1 | `별로에요` |
| 1 | 중립 | 0 | `보통` |
| 2 | 긍정 | +1 | `좋아요` |

이 매핑은 회귀 테스트로 고정해 두었습니다.

### E-c. 도메인 이동에 따른 성능 변화

**미션 13의 학습 도메인은 쇼핑몰, SNS 리뷰인데, 이번 추론 대상은 영화 리뷰(NSMC)입니다.**
성능 저하 가능성이 있어 NSMC test 3,000건(SEED=42)으로 실측했습니다.

NSMC는 이진 라벨(0=부정 / 1=긍정)이고 **중립 정답이 없습니다.** 그래서 지표를 둘로 나눴습니다.

| 지표 | 값 |
|---|---|
| 미션 13 자체 도메인 test accuracy | 0.885 |
| **NSMC 이진 정확도** (중립 예측 제외, 2,400건) | **0.818** |
| 엄격 정확도 (중립 예측을 오답 처리) | 0.654 |
| 중립 예측 비율 | 0.200 |

| 정답 \ 예측 | 긍정 | 부정 | 중립 |
|---|---|---|---|
| 부정(0) | 134 | 1,123 | 257 |
| 긍정(1) | 840 | 303 | 343 |

- **약 7%p 하락했습니다.** 재학습 없이 자산을 재사용한 결과입니다.
- 엄격 정확도 0.654는 **과소평가된 수치입니다.** NSMC에 중립 정답이 없어 중립 예측 600건이
  전부 오답으로 계산됩니다. 중립 예측은 확신도가 낮은 구간에 몰려 있어(0.9 미만에서 40~55%)
  모델의 **판단 유보**로 보는 편이 타당합니다.
- 부정 정답의 긍정 오분류(134건)보다 긍정 정답의 부정 오분류(303건)가 많습니다.
  **부정 쪽으로 치우친 예측 경향**이 있습니다.

### E-d. 저확신 예측 대응

`confidence`(= `max(softmax(logits))`) 구간별 정확도를 집계했습니다.

| confidence | 건수 | 엄격 정확도 | 이진 정확도 | 중립 예측 비율 |
|---|---|---|---|---|
| ~0.50 | 58 | 0.293 | 0.567 | 0.483 |
| 0.50~0.60 | 233 | 0.270 | 0.594 | 0.545 |
| 0.60~0.70 | 231 | 0.377 | 0.719 | 0.476 |
| 0.70~0.80 | 281 | 0.381 | 0.656 | 0.420 |
| 0.80~0.90 | 351 | 0.479 | 0.800 | 0.402 |
| 0.90~0.95 | 314 | 0.669 | 0.805 | 0.169 |
| **0.95~1.00** | **1,532** | **0.856** | **0.869** | 0.015 |

**confidence는 정확도와 단조에 가깝게 증가합니다.** 따라서 이를 저확신 표기의 기준으로 삼는 것이
실측으로 정당화됩니다. 0.90 미만 구간은 엄격 정확도가 0.5를 밑돌므로 **임계값을 0.90**으로 정했습니다.

대응 방식은 **표기까지만** 합니다. `confidence`로 예측을 보정하거나 뒤집지 않습니다.
저확신이면 화면에 `판정 애매` 배지를 덧붙이되 라벨은 그대로 보여줍니다.
모델의 판단을 감추지 않으면서 불확실성만 함께 전달하는 방법이고,
추가 의존성도 지연도 들지 않습니다.

### E-e. 입력 길이 제약 (truncation)

모델은 **Fixed Shape**이라 입력이 256 토큰으로 고정됩니다. 긴 리뷰가 어떻게 처리되는지
직접 확인했습니다.

| 사례 | 앞 200자만 | 전체(700자+, 잘림) |
|---|---|---|
| 앞=긍정 / 뒤=부정 | 긍정 0.988 | 긍정 0.578 |
| 앞=부정 / 뒤=긍정 | 부정 0.987 | **긍정 0.500** |

모델은 앞 256토큰만 보므로 **뒤쪽의 반전 문장은 판단에 반영되지 않습니다.**
다만 잘린 입력은 확신도가 0.50대로 급락해, 저확신 표기가 이 경우도 함께 걸러내는
부수 효과가 있습니다. 추론 결과에 `truncated` 플래그를 포함시켜 화면이 안내할 수 있게 했습니다.

## G. 데이터 출처와 한계

### G-a. 영화 메타데이터: TMDB API

**This product uses the TMDB API but is not endorsed or certified by TMDB.**
(이 서비스는 TMDB API를 사용하지만 TMDB가 보증하지 않습니다.)

출처 표기는 약관상 의무이므로 모든 화면에 노출되도록 사이드바에 고정했습니다.

감독은 `/movie/{id}` 응답에 없어 `/movie/{id}/credits`의 `crew`에서 `job == "Director"`로
따로 추출했습니다. 포스터는 **URL만 저장**하고 이미지 파일을 저장소에 복사하지 않았습니다.

### G-b. 리뷰: NSMC, 그리고 임의 배정이라는 한계

리뷰는 **NSMC**(네이버 영화 리뷰 20만 건) 공개 데이터셋에서 가져왔습니다.

> **주의: 리뷰와 영화의 대응은 임의 배정이며, 실제 해당 영화의 관람평이 아닙니다.**

NSMC는 영화별로 정리된 데이터가 아니라 리뷰 텍스트와 긍/부정 라벨의 모음입니다.
필드가 `id / document / label`뿐이라 **제목, 작성자, 등록일은 파생 생성**했습니다
(제목은 본문 첫 구절, 작성자는 `익명N`, 등록일은 분 단위로 흩뿌림).

TMDB 리뷰를 쓰지 않은 이유는 두 가지입니다. 대부분 영어라 한국어 모델에 넣을 수 없고,
영화당 편수가 적어 "각 영화당 리뷰 10건 이상" 요건을 채우지 못합니다.

### G-c. 시드 감성 분포도 연출입니다

첫 시도에서는 모든 영화에 같은 감성 비율을 배정했습니다. 그 결과 **6편의 평점이 전부 0.167로
동일**해져 화면에서 평점 차이를 확인할 수 없었습니다. 평균 평점 표시가 필수 요건인데
값이 모두 같으면 기능이 동작하는지 증명되지 않습니다.

그래서 TMDB 평점 순서에 대략 맞춰 영화별 배분을 다르게 했고, `판정 애매` 표기를 증명하기 위해
**정답과 일치하면서 확신도가 0.55~0.90인 리뷰**를 영화당 2건씩 포함시켰습니다.
어차피 리뷰와 영화의 대응 자체가 임의 배정이므로 **평점 값 자체에 의미는 없습니다.**

### G-d. 리뷰는 "어느 영화에 붙어도 자연스러운 것"만 고릅니다

임의 배정을 그대로 두니 기생충 리뷰에 이런 것들이 붙었습니다.

```
한지민 짱 최고최고 완전예쁨
진정한자아를 찾은 뮤리엘이 부럽다
짱CSI보다재밌어 나 구라안쳐요
```

명백히 다른 작품 이야기입니다. 임의 배정이라고 **문서에 적어 두더라도, 화면을 보는 사람은
먼저 "데이터가 깨졌나"로 읽게 됩니다.**

그래서 시드 선별에 **일반 평가문 필터**를 넣었습니다.

| 조건 | 방식 |
|---|---|
| 특정 작품, 인물 언급 제외 | 영문과 숫자, `~님/씨/배우/감독`, 원작/속편/시즌, TV 용어(본방, 시청률), 제작국 언급 |
| **희귀 어절 제외** | NSMC 15만 건 기준 문서 빈도 40 미만 어절이 하나라도 있으면 제외 |
| 평가 어휘 필수 | 재미, 연기, 연출, 스토리, 지루, 감동 등 최소 1개 포함 |
| 중복 제거 | NSMC에는 같은 문장이 다른 id로 여러 번 있어 서로 다른 영화에 중복 배정됩니다 |

희귀 어절 필터가 핵심입니다. `사이먼래틀`, `엄석대`, `하이바라` 같은 고유명사는
접미사 규칙으로 잡히지 않지만 **말뭉치에서 드물다**는 공통점이 있습니다.
형태소 분석기 없이 표준 라이브러리만으로 처리했습니다.

15만 건에서 후보 약 1,800건이 남았고, 그중 72건을 골랐습니다.
빈도 필터를 통과할 만큼 흔한 배우 이름(`견자단` 등)은 일반화가 불가능해 목록으로 따로 뺐습니다.

## H. 배포

### H-a. 배포 토폴로지

```mermaid
flowchart LR
    subgraph SRC["제출 전용 public 저장소"]
        FEDIR["frontend/"]
        BEDIR["backend/"]
    end

    BEDIR --> BUILD["이미지 빌드<br/>시드 DB, ONNX 포함"]
    BUILD --> CR["Cloud Run<br/>1GiB, max-instances=1"]
    FEDIR --> SC["Streamlit Community Cloud"]

    SC -.->|st.secrets 로 base URL 주입| CR
```

- **Vercel은 Streamlit을 구동할 수 없습니다.** 서버리스라 상시 프로세스와 WebSocket을 유지하지 못합니다.
- 백엔드 base URL은 하드코딩하지 않고 `st.secrets`를 먼저 보고 없으면 환경변수를 읽습니다.
- 아카이브 저장소에는 다른 미션의 실제 API 키가 존재하므로 private을 유지하고,
  **미션 18 코드만 담은 별도 public 저장소**를 만들어 배포용으로 씁니다.

### H-b. SQLite와 컨테이너의 제약 실측

컨테이너 파일시스템에 쓰는 SQLite는 인스턴스가 교체되면 사라집니다.
로컬 컨테이너로 이 상황을 재현해 확인했습니다.

|---|---|

운영을 전제한다면 Cloud SQL 같은 외부 DB로 바꿔야 하지만, 이번 미션의 평가 대상이 아닙니다.

### H-e. 공개 배포본의 삭제 방어

배포하고 나니 **누구나 시드 영화를 삭제할 수 있고, 리뷰 12건이 함께 사라지는** 상태였습니다.
UI상에는 화면의 2단계 확인(체크박스)뿐인데 고의로 지우면 막을 방법이 없습니다.
"인스턴스를 교체해 시드로 복원하는 것"도 **언제 삭제될지 알 수 없어** 답이 아니라고 판단했습니다,
하필 평가 중에 화면이 비어 있으면 의미가 없기 때문입니다.

그렇다고 삭제 기능을 없앨 수는 없습니다. **영화 삭제는 가이드의 필수 기능**입니다.

그래서 **시드 데이터만 보호**하기로 했습니다.

| 대상 | 로컬 실행 | 공개 배포본 |
|---|---|---|
| 시드 영화와 그 리뷰 (`is_seed=true`) | 삭제 가능 | **403 차단** |
| 사용자가 직접 등록한 영화 | 삭제 가능 | 삭제 가능 |

- `PROTECT_SEED` 환경변수로 켜고 끕니다. **배포본에서만 켭니다.**
- 시드 영화의 **리뷰 삭제도 함께 막습니다.** 영화만 막으면 리뷰를 하나씩 지워
  같은 결과(빈 화면)를 만들 수 있습니다.
- 삭제 가능 여부는 **서버가 판단해 `deletable` 필드로 내려줍니다.** 화면이 스스로
  규칙을 갖지 않게 했습니다. 규칙이 두 곳에 있으면 언젠가 어긋나기 때문입니다.
- 필수 기능 시연은 그대로 가능합니다. 영화를 하나 등록한 뒤 지우면 됩니다.

시드 영화의 위험 구역은 아래처럼 삭제 버튼이 비활성화되고 이유가 함께 표시됩니다.

![시드 보호, 삭제 차단](captures/12_시드보호_삭제차단.png)

배포본 실측 결과입니다.

| 요청 | 결과 |
|---|---|
| `DELETE /movies/1` (시드) | **403**, "데모 시드 데이터는 삭제할 수 없습니다" |
| `DELETE /reviews/1` (시드 영화의 리뷰) | **403** |
| `DELETE /movies/{신규 등록}` | **204**, 필수 기능 정상 동작 |
| 시드 무결성 | 영화 6편, 리뷰 72건 유지 |

### H-f. 배포에서 걸린 지점

기록해 둘 만한 실패가 네 번 있었습니다.

1. **결제 계정이 닫혀 있으면 아무것도 되지 않습니다.** 계정 등록 여부가 아니라
   `gcloud billing accounts list`의 `OPEN` 열을 봐야 합니다.
2. **API 활성화 직후 권한이 바로 붙지 않습니다.** IAM에 `roles/owner`가 정상 부여돼 있는데도
   `artifactregistry.repositories.create`가 `PERMISSION_DENIED`로 실패했습니다.
   45초 간격 재시도로 통과했습니다. 전파 지연입니다.
3. **프론트엔드가 백엔드를 못 찾았습니다.** Streamlit Secrets에 `BACKEND_BASE_URL`이 없어
   기본값(`localhost:8000`)으로 요청했고, 화면에는 "백엔드에 연결할 수 없습니다"만 떴습니다.
   백엔드는 정상이었으므로 **원인 진단이 불가능한 메시지**였습니다.
   그래서 오류 배너에 **요청 대상 주소**를 노출하고, 기본값을 쓰는 중이면 설정이 필요하다는
   안내를 덧붙이도록 고쳤습니다. 주소가 틀린 것과 서버가 죽은 것은 대응이 다릅니다.
4. **SQLite WAL 때문에 이미지에 옛 DB가 들어갔습니다.** 시드 보호 기능을 넣고 배포했더니
   `no such column: movie.is_seed`로 500이 났습니다. 로컬에서는 멀쩡했는데,
   앱이 연결마다 `PRAGMA journal_mode=WAL`을 걸기 때문에 스키마 변경이
   `movies.db-wal`에만 남아 있었고 `.dockerignore`가 그 파일을 제외한 것입니다.
   **`movies.db` 하나만 복사되면서 변경분이 통째로 사라졌습니다.**
   그래서 시드 스크립트 마지막에 `wal_checkpoint(TRUNCATE)`와 `journal_mode=DELETE`를
   수행해 **DB가 단일 파일로 완결되게** 만들었습니다. 저널 모드 전환에는 배타적 잠금이
   필요하므로 세션을 모두 닫은 뒤 전용 연결로 실행합니다.

## I. 성능 실측

컨테이너(`--memory=1g --cpus=1`, Cloud Run 상당) 기준입니다.

### I-a. 응답 지연

| 엔드포인트 | p50 | p95 |
|---|---|---|
| `GET /movies` | 3.8ms | 4.9ms |
| `POST /sentiment/analyze` | 76.4ms | 82.7ms |
| `POST /reviews` (추론 포함) | 83.1ms | 91.4ms |

**추론이 지연의 대부분**을 차지하고 DB 조회는 4ms 안쪽입니다.
추론을 등록 시 1회로 제한한 설계가 조회 화면의 응답성을 지켜 줍니다.

`intra_op_num_threads=1`로 고정해 측정했습니다. Cloud Run 1 vCPU를 가정한 값이며,
스레드 제한이 없던 미션 13 측정(p50 29ms)보다 느린 이유이기도 합니다.

### I-b. 메모리

| 시점 | 사용량 |
|---|---|
| 기동 직후 (모델 로드 완료) | 153.3 MiB |
| 부하 후 피크 | **168.2 MiB / 1 GiB (16.4%)** |

계획 단계의 추정 피크는 400~600MB였는데 **실측은 그 절반 이하**였습니다.
`transformers` 없이 `tokenizers`만 쓴 선택이 실제로 효과를 냈습니다.
예산에 여유가 크므로 추가 대응은 하지 않았습니다.

### I-c. 테스트

`pytest` 26건이 통과합니다. 상태 코드별 검증, 페이지네이션 경계(0건 / 10건 / 11건),
연쇄 삭제, 모델 미로드 시 폴백, OpenAPI 설명 누락 검사, 라벨 매핑 회귀 테스트를 포함합니다.

## J. 마무리

### J-a. 이번 미션에서 판단이 갈렸던 지점

| 지점 | 선택 | 이유 |
|---|---|---|
| 평점 캐시 여부 | 캐시하지 않고 조회 시 집계 | 갱신 경로 3곳 중 하나만 빠뜨려도 평점에 이상이 생깁니다 |
| 리뷰 0건 평점 | `null` (0이 아님) | 0은 '중립'의 의미를 갖습니다 |
| 추론 실패 시 응답 | 201 (감성 필드만 `null`) | 리뷰 저장 자체는 성공했습니다 |
| 모델 로드 실패 | 앱을 죽이지 않음 | 영화 CRUD는 필수 기능이고 모델과 무관합니다 |
| 저확신 대응 | 표기만, 보정 없음 | 관측치 없이 보정 장치를 먼저 만들지 않습니다 |
| 공개 배포본 삭제 | 시드만 보호 | 필수 기능(삭제) 시연과 데모 보존을 동시에 만족합니다 |
| 토크나이저 | `tokenizers` 단독 | 메모리 예산에 직접 영향 |

### J-b. 남은 한계

1. **리뷰와 영화의 대응이 임의 배정**이라 평점 값 자체에는 의미가 없습니다.
   실제 서비스라면 영화별 실 리뷰를 수집해야 합니다.
2. **도메인 이동으로 정확도가 약 7%p 낮습니다.** 영화 리뷰로 추가 파인튜닝하면 회복 가능하지만,
   이번 미션의 목적은 통합이지 모델 재학습이 아니라 범위 밖으로 두었습니다.
3. **중립 클래스가 가장 불안정합니다.** 골든 케이스에서도 유일한 오분류가 중립이었고,
   확신도 역시 중립에서 가장 낮았습니다. 3단 표기를 유지하려면 중립 라벨의 학습 데이터 보강이 필요합니다.
4. **배포본의 데이터는 영속되지 않습니다.** 데모 목적에서는 문제가 없지만
   운영에는 외부 DB가 필요합니다.
