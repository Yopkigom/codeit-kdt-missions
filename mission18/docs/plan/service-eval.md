# 미션 18 서비스 통합 실측 기록 (I 섹션)

시드 데이터를 적재한 뒤 수행한 end-to-end 검증과 자원·지연 실측이다.
모델 자체의 실측은 [model-eval.md](model-eval.md)에 있다.

## A. 시드 데이터 (F 섹션 결과)

영화 6편 · 리뷰 72건(영화당 12건). 캡처 요건은 영화 3편 이상 · 영화당 리뷰 10건 이상이다.

| 영화 | 감성 평점 | 별점 환산 | TMDB 평점 | 긍/중/부 | 저확신 |
|---|---|---|---|---|---|
| 기생충 | 0.583 | 4.0 | 8.49 | 9 / 1 / 2 | 2 |
| 부산행 | 0.333 | 3.3 | 7.75 | 7 / 2 / 3 | 2 |
| 올드보이 | 0.333 | 3.3 | 8.23 | 7 / 2 / 3 | 2 |
| 신세계 | 0.167 | 2.9 | 7.40 | 6 / 2 / 4 | 2 |
| 괴물 | 0.000 | 2.5 | 7.00 | 5 / 2 / 5 | 2 |
| 헤어질 결심 | -0.083 | 2.3 | 7.30 | 4 / 3 / 5 | 2 |

### A-a. 영화별로 감성 구성을 다르게 한 이유

첫 시도에서는 모든 영화에 같은 비율(긍6 · 중2 · 부4)을 배정했다. 그 결과
**6편의 감성 평점이 전부 0.167로 동일**해져 화면에서 평점 차이를 확인할 수 없었다.
평균 평점 표시가 필수 요건인데 값이 모두 같으면 기능이 동작하는지 화면으로 증명되지 않는다.

→ TMDB 평점 순서에 대략 맞춰 영화별 프로필을 다르게 배정했다.
**이 배분은 연출이다.** 애초에 리뷰-영화 대응 자체가 임의 배정이므로
평점 자체에 의미를 부여하지 않으며, 이 사실을 보고서에 명시한다.

### A-b. 저확신 표본을 의도적으로 포함한 이유

시드를 확신도 0.90 이상만으로 채우면 `판정 애매` 배지가 화면에 **한 번도 나타나지 않는다.**
영화당 2건씩, NSMC 정답과 **일치하면서** 확신도가 0.55~0.90인 리뷰를 포함시켰다.
틀린 예측을 넣은 것이 아니라 불확실한 예측을 넣은 것이다.

## D. 지연 실측 (I-b-3)

컨테이너(`--memory=1g --cpus=1`, Cloud Run 상당) 기준이다.

| 엔드포인트 | p50 | p95 |
|---|---|---|
| `GET /movies` | 3.8ms | 4.9ms |
| `POST /sentiment/analyze` | 76.4ms | 82.7ms |
| `POST /reviews` (추론 포함) | 83.1ms | 91.4ms |

- **추론이 지연의 대부분**을 차지한다. DB 조회는 4ms 안쪽이다.
- 미션 13 측정(PyTorch CPU p50 29ms)보다 느린 것은 `intra_op_num_threads=1`로
  스레드를 고정했기 때문이다. Cloud Run 1 vCPU 환경을 가정한 값이다.
- 추론을 **등록 시 1회**만 수행하므로 목록·상세 조회는 이 비용을 물지 않는다.
  조회 시마다 추론했다면 리뷰 10건 페이지가 800ms대가 됐을 것이다.

## E. 메모리 실측 (I-b-4)

| 시점 | 사용량 |
|---|---|
| 기동 직후 (모델 로드 완료) | 153.3 MiB |
| 부하 후 피크 | **168.2 MiB / 1 GiB (16.4%)** |

- 계획 단계의 추정 피크는 400~600MB였는데 **실측은 그 절반 이하**다.
  `transformers` 없이 `tokenizers`만 쓴 선택(implementation.md B-e)이 효과를 냈다.
- 이미지 크기는 752MB이며 대부분 ONNX 자산(127MB)과 onnxruntime 의존성이다.
- 예산에 여유가 크므로 **대응이 필요한 초과 항목은 없다**(I-c-1).

## F. SQLite 비영속성 확인 (J-c-3 사전 검증)

로컬 컨테이너로 Cloud Run의 인스턴스 교체 상황을 재현했다.

| 조작 | 리뷰 수 |
|---|---|
| 시드 상태 | 72건 |
| 리뷰 30건 추가 후 | 102건 |
| `docker restart` (같은 컨테이너) | 102건 — **유지됨** |
| 새 컨테이너 기동 (인스턴스 교체 상당) | **72건 — 시드로 복귀** |

컨테이너 재시작은 쓰기 레이어를 유지하므로 데이터가 남지만, 인스턴스가 교체되면
런타임에 추가된 데이터가 사라진다. 설계 문서에 적어 둔 제약이 실제로 그렇게 동작함을 확인했다.

→ **배포본은 데모용이며 영속 저장은 로컬 실행 기준**임을 보고서에 명시한다.
`--max-instances=1`로 고정해 인스턴스 간 DB 불일치도 함께 막는다.
